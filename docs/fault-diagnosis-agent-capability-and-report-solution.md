# 故障诊断 Agent：运行查询、诊断能力与工业运行报告改进方案

> 文档状态：方案稿，不包含代码修改
>
> 调研与代码核查日期：2026-08-06
>
> 适用范围：当前 `FAULT_DIAGNOSIS + DETERMINISTIC` 专用 Agent、`ruoyi-fault` 模块、用户聊天端
>
> 前提：当前主要使用模拟遥测，故障诊断仍以显式故障码/报警码为事实依据

## 1. 结论先行

当前问题不是“提示词少写了几个任务”，而是系统把三种不同性质的能力压进了一条以故障码为中心的诊断链：

1. **运行观测**：回答设备现在/某时段“实际发生了什么”，例如当前转速、过去一小时平均转速、温度趋势；
2. **故障知识查询**：回答某个故障码在手册中“是什么意思、如何处理”，不读取设备数据；
3. **故障诊断**：结合设备遥测、故障码、规则和知识资料，对异常进行有证据边界的判断；
4. **运行报告**：对一个明确时间窗内的运行事实、趋势、事件和数据质量做结构化汇总，可附带诊断章节，但不等同于诊断本身。

建议仍保留**一个专用 Agent 和一条确定性编排链**，不引入新的多 Agent，也不允许模型生成 SQL。核心改动是：把“故障诊断 Agent”从固定问句分类器改成一个由受控能力组成的设备运维助手，其中运行数据查询成为独立的一等能力。

推荐目标链路：

```text
用户问题
  → 请求规划（识别要使用的能力和参数，不下结论）
  → 服务端校验（资产权限、指标目录、时间窗、聚合函数）
  → 一次受控遥测窗口读取与标准化
       ├─ 运行指标查询：最新值 / 采样平均 / 最小 / 最大 / 趋势
       ├─ 运行状态摘要：数据新鲜度 + 运行模式 + 关键指标 + 当前事件
       ├─ 故障诊断：显式代码 + 规则 + 知识库 + 证据
       └─ 运行报告：运行事实 + KPI + 趋势 + 事件 + 数据质量 + 可选诊断
  → 确定性结果渲染；LLM 只做规划和有限的文字整理
```

这不是通用 BI、自然语言 SQL 或自动控制平台。第一阶段只覆盖现有遥测表中已确认语义和单位的指标，以及少量明确的统计操作。

## 2. 当前实现核查与根因

### 2.1 任务边界在代码和提示词中同时被封闭

当前不是“好像只有几类”，而是后端明确只允许三类：

- `FaultTaskType` 只有 `DIAGNOSE`、`EXPLAIN_FAULT_CODE`、`GENERATE_REPORT`；
- `FaultRequestPlanner.SYSTEM` 明确要求模型只能从上述三类中选择；
- `FaultDiagnosisChatService.normalize()` 在有设备、时间或症状但没有合法任务时，默认补成 `DIAGNOSE`；
- 除报告和纯故障码查询外，其余路径最终进入 `FaultDiagnosisOrchestrator`。

因此“G120 电机 1 最近半小时转速是多少”即使被模型识别出设备和时间，也只能被迫进入故障诊断；如果模型未按三种任务输出，就会返回截图中的“请说明需要诊断的设备……”提示。

涉及文件：

- `ruoyi-modules/ruoyi-chat/src/main/java/org/ruoyi/service/fault/model/FaultTaskType.java`
- `ruoyi-modules/ruoyi-chat/src/main/java/org/ruoyi/service/fault/FaultRequestPlanner.java`
- `ruoyi-modules/ruoyi-chat/src/main/java/org/ruoyi/service/fault/FaultDiagnosisChatService.java`

### 2.2 数据存在，但在“诊断摘要化”后丢失

`RealDataEntity` 已包含：

- 直流电压；
- 速度设定值、实际速度；
- 实际电流；
- 转矩设定值、实际转矩；
- 进气、电机、逆变器、散热器温度；
- 实际功率；
- 逆变器和电机负载率。

`RealDataMapper` 也已经读取这些字段。但是 `TelemetryStatistics` 只保留了实际功率、少量温度和负载率统计，没有保留转速、电流、转矩、电压，也没有通用的最新值或指定指标聚合结果。原始时序在 `TelemetryDataAnalyzer` 之后不再可用。

所以问题不是数据库没有转速，而是现有遥测服务被定义成“给诊断编排器的有限摘要”，却又被报告和所有运行问题复用。

### 2.3 “运行状态”和“诊断状态”被合成了一个状态

当前 `OperationReportOrchestrator` 直接由 `DiagnosisStatus` 映射 `ReportHealthStatus`，报告标题也叫“设备运行与状态报告”。这会产生两个语义扩大：

- “窗口内没有 F/A 代码”被展示成“正常”，但它只能证明**没有观测到显式代码**，不能证明转速、温度、负载、通信和机械状态均正常；
- 用户问“运行状态”时，系统主要回答有没有故障码，而不是给出最后更新时间、实际转速、设定/实际偏差、电流、负载、温度等运行事实。

正确做法不是再换一段措辞，而是分开四个维度：

| 维度 | 回答的问题 | 第一阶段可用值 |
| --- | --- | --- |
| 数据状态 | 数据能否代表现在 | `FRESH / STALE / NO_DATA` |
| 运行模式 | 设备是否在运行、停止等 | `RUNNING / STOPPED / UNKNOWN`，前提是状态字典已确认 |
| 事件状态 | 当前是否有报警/故障事件 | 无活动代码 / 报警 / 故障 / 未识别代码 |
| 诊断结论 | 是否执行诊断、诊断发现什么 | 未执行 / 数据不足 / 检测到显式代码 / 有限诊断结论 |

同一设备可以是“数据新鲜、正在运行、存在报警、未执行根因诊断”，不应被压缩成一个“关注”或“故障”。

### 2.4 报告短并不只是文案问题

当前报告有以下结构性限制：

1. 聊天入口刻意调用 `renderConcise()`，完整版只在下载接口生成；用户在聊天中看见的本来就是删减版；
2. 配置中的 `metric-units` 为空时，所有运行指标都会隐藏，报告自然只剩故障码、报警码和建议；
3. 报告没有实际转速、设定/实际偏差、电流、转矩、电压等核心运行指标；
4. 没有时序曲线，无法回答“期间如何变化、事件前后有什么变化”；
5. 报告的健康状态仍来自故障诊断状态，内容重心天然落在代码而非运行；
6. `/generate` 与 `/download` 会分别重新查询并生成报告，报告编号和数据快照可能不同，当前并不存在真正的“先查看同一份报告，再下载它”。

涉及文件：

- `ruoyi-modules/ruoyi-fault/src/main/java/org/ruoyi/fault/report/MarkdownOperationReportRenderer.java`
- `ruoyi-modules/ruoyi-fault/src/main/java/org/ruoyi/fault/report/OperationReportOrchestrator.java`
- `ruoyi-modules/ruoyi-chat/src/main/java/org/ruoyi/controller/fault/OperationReportController.java`
- `ruoyi-admin/src/main/resources/application.yml`

### 2.5 “最近数据回退”不适合所有运行问题

`TelemetryQueryService` 当前使用一个全局开关：请求窗口没有数据时，自动换成设备最近可用的另一段窗口。这个策略对模拟阶段的演示有帮助，但不能成为通用查询语义：

- 问“此时转速”时，可以补充“最后已知值”，但必须显示时间和已过期状态；
- 问“过去一小时平均转速”时，不能换成另一小时的数据再计算；
- 生成指定周期运行报告时，不能悄悄改变报告周期。

因此回退策略应成为请求的一部分，而不是全局行为：

- `EXACT_WINDOW`：统计、趋势、历史报告默认使用，窗口无数据就如实返回无数据；
- `LAST_KNOWN_ALLOWED`：仅用于当前值/状态查询，返回最后已知值时明确标注时间和新鲜度，绝不称为“当前值”。

## 3. 工业资料调研结论

本节资料用于提炼通行结构，不表示本项目已经符合或通过任何标准认证。

### 3.1 运行监测需要从运行参数出发，不以故障码代替

- [ISO 17359:2018](https://www.iso.org/standard/71194.html) 给出建立机器状态监测方案的一般程序，适用于各类机器；
- [ISO 13379-1:2025](https://www.iso.org/standard/88027.html) 明确机器状态可以通过运行参数（输入）和响应参数（输出）的测量或观测来描述；
- [ISO 13374-1:2003](https://www.iso.org/standard/21832.html) 将状态监测软件关注点概括为数据处理、通信和信息呈现；[ISO 13374-2:2007](https://www.iso.org/standard/36645.html) 进一步强调参考信息模型和处理模型。

对本项目的直接启示是：运行查询、数据处理、诊断和报告呈现应该共享数据契约，但不能互相替代。

### 3.2 工业时序统计必须有清晰的聚合口径和数据质量

[OPC UA Part 13: Aggregates](https://reference.opcfoundation.org/Core/Part13/v105/docs/) 定义了 Average、TimeAverage、Minimum、Maximum、最值实际时间、状态持续时间、状态切换次数，以及 PercentGood、PercentBad、WorstQuality 等聚合/质量语义。

本项目第一阶段不需要全部实现，但至少要做到：

- 清楚区分最新值、采样平均值、最小值、最大值和趋势；
- 平均值说明是“采样算术平均”还是“时间加权平均”；
- 所有统计同时返回时间窗、样本数、完整率、缺口和单位；
- 无数据返回空值，不能用 0 代替；
- 统计窗口无数据时不能换窗计算。

为避免过度设计，第一阶段只实现 `LATEST / AVG_SAMPLES / MIN / MAX / TREND`。当前采样基本等间隔时使用 `AVG_SAMPLES`，对用户明确写成“采样平均值”；只有真实数据确认存在不规则采样且业务需要时，再增加 `TIME_AVG`。

### 3.3 工业运行报告的重心是 KPI、趋势、目标/边界和事件上下文

- Siemens 的[状态监测应用介绍](https://www.siemens.com/en-us/content/condition-monitoring-apps/)将报警、轴电机工时、当前负载、转速和温度放在预测维护监测中，并说明报告会包含 KPI 及其趋势/目标、上下文图表、利用率/停机时间和生产中断统计；
- Siemens `Analyze MyDrives` 的[操作手册](https://support.industry.siemens.com/cs/attachments/109810356/amdc_op_man_1021_en-US_en-US.pdf?download=true)在设备概览中展示 Ready/Run/Alarm/Fault 数量、实际功率、最后更新时间、最后故障和资产状态，并对长时间未更新的数据给出明显提示；
- [IBM Maximo Monitor](https://www.ibm.com/docs/en/masv-and-l/maximo-monitor/cd?topic=overview-maximo-monitor)将当前/历史趋势、计算指标、异常点和报警放在同一个可下钻视图中；
- [Azure IoT Central Dashboard](https://learn.microsoft.com/en-us/azure/iot-central/core/howto-manage-dashboards)区分最新值、区间 KPI、折线趋势、事件历史和状态历史，并支持平均、最小、最大、计数等聚合；其[设备属性模型](https://learn.microsoft.com/en-us/azure/iot-central/core/howto-use-properties)也把语义类型、单位和显示单位作为指标定义的一部分。

这说明可读性不是把说明段落写长，而是让读者先看懂状态和关键数，再沿趋势、事件和证据下钻。

### 3.4 报警应当作为事件生命周期呈现

- [IEC 62682:2022](https://webstore.iec.ch/en/publication/65543)说明报警系统的主要作用是通知操作员异常工况或设备异常并支持响应；
- [ISA-18 系列](https://www.isa.org/standards-and-publications/isa-standards/isa-18-series-of-standards)强调报警的目标、分类、优先级、监测和持续优化；监测指标包括报警率、长期未清除报警和响应时间；
- Rockwell FactoryTalk 的[报警事件历史说明](https://www.rockwellautomation.com/en-us/docs/factorytalk-services-platform/6-60/factorytalk-services-platform-help-ditamap/factorytalk-alarms-and-events-help/use-tag-based-alarm-monitoring/alarm-and-event-history-logging.html)记录进入报警、退出报警、确认、抑制、启用/禁用等状态变化。

当前报告的“采样命中 30 条”不是“发生 30 次”。后续应优先形成事件生命周期：开始时间、结束/持续中、持续时长、恢复状态；只有模拟数据无法可靠重建事件时，才保留“包含该代码的采样数”并明确其含义。

### 3.5 展示应服务于态势感知，而不是堆叠大标题和长文本

[ISA-101 系列](https://www.isa.org/standards-and-publications/isa-standards/isa-101-standards)强调以人为中心的 HMI、有效的信息层级、直观交互、可用性和态势感知。对聊天中的运行报告，适合采用“摘要先行、异常突出、图表下钻、证据后置”的层级；颜色只用于状态和异常，不应让所有标题都争夺注意力。

## 4. 目标能力模型

### 4.1 仍然允许有限能力，但不枚举所有问法

任何可控系统都需要有限的后端能力边界。问题不在于“存在枚举”，而在于当前枚举把每种用户问题当成一个任务，并且没有可参数化的运行查询。

建议规划器只在以下**证据/执行能力**间选择：

| 能力 | 作用 | 是否读遥测 | 是否执行诊断 |
| --- | --- | --- | --- |
| `QUERY_TELEMETRY` | 最新值、区间统计、趋势、运行状态摘要 | 是 | 否 |
| `LOOKUP_FAULT_CODE` | 查询故障/报警手册 | 否 | 否 |
| `DIAGNOSE_FAULT` | 根据遥测代码、规则和知识进行诊断 | 是 | 是 |
| `GENERATE_OPERATION_REPORT` | 汇总一个精确窗口的运行事实，可附诊断章节 | 是 | 可选且显式 |

“当前转速”“过去一小时平均转速”“最高电机温度”“转速趋势”都属于同一个 `QUERY_TELEMETRY`，差别只在参数，不再增加任务枚举。

复合问题可以形成多个步骤，但共享同一个标准化遥测窗口。例如“给出最近一小时运行报告，并说明其中的 F30899”可以生成报告并查询代码知识；不需要调用通用 Supervisor 或多个 Agent。

### 4.2 引入小而明确的指标目录

不要把数据库列名直接交给模型，也不要允许模型拼 SQL。增加服务端指标目录，第一阶段可直接用 Java 常量/配置实现，不需要新建元数据平台。

建议每个指标至少包含：

```text
key               稳定业务键，例如 speed_actual
displayName       实际转速
aliases           转速、当前速度、实际速度
sourceField       RealDataEntity::getSpeedActual（仅服务端可见）
valueType         NUMBER / STATE / CODE
engineeringUnit   rpm（必须经数据字典确认）
precision         1
allowedOperations LATEST, AVG_SAMPLES, MIN, MAX, TREND
enabled           是否对外可查询
```

建议首批纳入现有字段：

| 业务指标 | 字段 | 首批操作 | 前置条件 |
| --- | --- | --- | --- |
| 实际转速 | `speedActual` | 最新、平均、最小、最大、趋势 | 确认工程单位 |
| 转速设定值 | `speedSetpoint` | 最新、平均、趋势 | 确认工程单位 |
| 实际电流 | `currentActual` | 最新、平均、最大、趋势 | 确认工程单位 |
| 实际转矩 | `torqueActual` | 最新、平均、最小、最大、趋势 | 确认工程单位和正负值含义 |
| 实际功率 | `actualPower` | 最新、平均、最小、最大、趋势 | 确认工程单位 |
| 电机/逆变器温度 | 对应温度字段 | 最新、平均、最大、趋势 | 确认单位 |
| 电机/逆变器负载率 | 对应负载字段 | 最新、平均、最大、趋势 | 确认是否已经是百分数 |
| 直流侧电压 | `dcVoltage` | 最新、平均、最小、最大、趋势 | 确认单位 |

单位未确认的指标必须标成“暂不可对外查询”，而不是继续像当前报告一样把整个运行指标章节静默隐藏。回答应说明“字段存在，但工程单位尚未确认”。

### 4.3 使用结构化查询计划，而非为每句话写正则

建议的规划结果示例：

```json
{
  "steps": [
    {
      "capability": "QUERY_TELEMETRY",
      "asset": "G120电机1",
      "timeRange": { "kind": "RECENT", "minutes": 60 },
      "metrics": ["speed_actual"],
      "operations": ["AVG_SAMPLES"],
      "fallbackPolicy": "EXACT_WINDOW",
      "presentation": "VALUE"
    }
  ]
}
```

“此时转速是多少”则使用 `LATEST + LAST_KNOWN_ALLOWED`；“画最近一小时转速趋势”使用 `TREND + EXACT_WINDOW + SERIES`。

模型只负责从自然语言映射到这些参数。服务端必须继续校验：

- 资产是否在用户授权范围；
- 指标是否在目录且已启用；
- 聚合是否对该指标开放；
- 时间窗是否完整且不超过上限；
- 趋势点数是否超过限制；
- 不接受 SQL、表名、字段名、知识库 ID 或任意函数名。

指标目录和允许操作应由服务端动态附给规划器，而不是在提示词正文中复制一份长期失真的清单。

### 4.4 共享遥测窗口，分别构造不同视图

建议在现有 `TelemetryQueryService` 与 `TelemetryDataAnalyzer` 基础上做职责拆分，不另建通用查询平台：

```text
TelemetryWindowService
  - 资产/时间/表路由校验
  - 读取固定列
  - observedAt 解析、精确过滤、去重、排序
  - 数据质量、来源摘要
  - 输出仅在服务端内部使用的标准化 TelemetryWindow

TelemetryMetricQueryService
  - 根据 MetricCatalog 提取一个或多个指标
  - 计算 latest / avg / min / max / trend
  - 输出值、单位、时间、样本数、质量、是否最后已知值

TelemetryDiagnosisAnalyzer
  - 延续现有 F/A/未知代码归类、状态事件和诊断摘要

OperationReportAssembler
  - 从同一 TelemetryWindow 组装运行报告
  - 可选择调用诊断分析，但不由诊断状态定义整个报告
```

这样既不会将原始遥测直接暴露给 LLM，也避免先丢失转速等数据、后面再重复查库。现有白名单、受控表路由、固定 Mapper 和最大时间窗限制可以继续保留。

## 5. 运行状态回答应该是什么

### 5.1 回答结构

用户问“查询 G120 电机 1 状态”时，默认返回一个**运行快照**，不是诊断报告：

```text
G120电机1 运行快照

数据状态：新鲜（最后更新 2026-08-06 13:48:00，距查询时刻 3 秒）
运行模式：运行中（依据已确认的 status 映射）
事件状态：存在 A07089 报警；未发现 F 类故障码

关键运行值
- 实际转速：812.4 rpm；设定转速：800.0 rpm；偏差：+12.4 rpm
- 实际电流：0.72 A
- 实际转矩：0.08 N·m
- 实际功率：0.11 kW
- 电机温度：39.2 ℃；逆变器温度：30.1 ℃
- 电机负载率：58.0%

说明：这是运行数据查询，未执行故障根因诊断。
数据来源：模拟遥测；仅用于功能演示。
```

只有确认状态字段/状态字的业务映射后才能显示“运行中/停止”。在此之前应显示“运行模式：未知（状态字典未确认）”，不能把当前脚本中的 `0/42` 直接解释成真实设备运行模式。

### 5.2 当前值必须带新鲜度

第一阶段只需要简单的三态，不必建设复杂在线状态机：

- `FRESH`：最后观测时间在配置的新鲜度阈值内；
- `STALE`：有最后值但已经超过阈值，只能称“最后已知值”；
- `NO_DATA`：设备没有可用值。

阈值按数据源或资产配置，并结合真实采样周期确定；不要把 Siemens 产品中的“一小时”提示直接复制为本项目阈值。

### 5.3 区间统计回答必须公开口径

“统计过去一小时转速平均值”的预期回答：

```text
G120电机1 在 2026-08-06 12:48:00—13:48:00 的实际转速采样平均值为 798.6 rpm。

口径：对窗口内 897 个有效 speed_actual 样本做算术平均；
数据完整率：99.7%，缺失 3 个采样点；未使用其他历史窗口补数。
数据来源：模拟遥测，仅用于功能演示。
```

平均、最小、最大等数值由确定性服务计算，LLM 不参与运算。

## 6. 工业运行报告 V2 方案

### 6.1 先明确报告用途

建议报告正式命名为**设备运行报告**，诊断只是其中一个可选章节。聊天中的“状态查询”不生成报告；用户明确说“报告、导出、下载”时才进入报告能力。

第一阶段只做一种“单设备、指定时间窗运行报告”，支持最近 N 分钟/小时、班次或明确起止时间。先不要同时设计日报、周报、车间汇总和多设备排行。

### 6.2 报告信息层级

#### 第一屏：让值班人员 10 秒内看懂

1. **报告标题与身份**：设备、逆变器、请求周期、实际数据周期、生成时间、报告编号；
2. **醒目数据标签**：`模拟数据` 或 `真实数据`；历史/过期数据必须有明显横幅；
3. **四类状态条**：数据状态、运行模式、报警/故障状态、诊断状态，避免一个“正常/关注/故障”包办全部语义；
4. **执行摘要**：3—5 句，只回答运行情况、主要变化、重要事件、是否需要行动；
5. **关键指标卡**：最新值、平均值、最小值、最大值、单位；没有阈值时不显示红黄绿评级。

#### 第二层：帮助定位变化

6. **运行趋势**：
   - 设定转速与实际转速放在同一张图；
   - 电机/逆变器温度放在同单位图；
   - 电流、转矩、功率、负载按单位分图，不在一个 Y 轴混画；
   - 报警/故障开始和恢复作为时间轴标记；
   - 图表显示时间范围、单位、采样/降采样方式和数据缺口。
7. **指标统计表**：指标、最新、平均、最小、最大、最值时间、样本数、单位；
8. **运行模式统计**：运行/停止时长和切换次数，仅在状态字典确认后展示；
9. **事件时间线**：代码、类型、开始、结束/持续中、持续时间、恢复状态、手册命中。当前只能得到采样命中时，明确写“包含代码的采样数”，不要写“发生次数”。

#### 第三层：帮助处置与追溯

10. **诊断与建议**：只有实际执行诊断时才出现；把“观测事实”“手册可能原因”“建议动作”分开；
11. **数据质量**：预期/有效样本、完整率、缺口、重复、无效时间、最后更新时间、查询是否精确命中；
12. **限制与缺失项**：未配置单位、未配置阈值、模拟数据、未接振动数据、未执行根因模型等；
13. **证据与审计附录**：数据摘要、知识文档、规则、EV 编号。聊天预览默认折叠，导出报告保留。

### 6.3 推荐的报告骨架

```text
设备运行报告                                      [模拟数据]
G120电机1 / G120电机1     2026-08-06 13:18—13:48

[数据：新鲜] [运行：运行中] [事件：A07089 已恢复] [诊断：未执行根因诊断]

执行摘要
周期内设备持续有数据；实际转速采样平均 798.6 rpm……
A07089 报警于 13:30:00 出现，13:31:56 恢复。

关键指标
实际转速    最新 812.4   平均 798.6   最低 741.0   最高 854.2 rpm
实际电流    最新 0.72    平均 0.63    最低 ...     最高 ... A
电机温度    最新 39.2    平均 38.7    最低 ...     最高 ... ℃

趋势
[设定/实际转速曲线，叠加报警时间标记]
[温度曲线]
[负载/功率曲线]

事件时间线
13:30:00  A07089 报警开始
13:31:56  A07089 恢复，持续 1分56秒

诊断与建议（仅在执行时出现）
数据质量与报告边界
证据附录
```

### 6.4 聊天预览与下载不应是两份重新计算的报告

推荐分两步演进：

- **P0**：聊天中展示有用的报告摘要、关键指标、事件和至少一张主趋势，不再只显示“请下载完整版”；下载接口暂时仍可导出；
- **P1**：生成报告时固化结构化 `ReportSnapshot`，返回 `reportCode`；查看和下载都按该编号读取同一快照，不能重新查询。导出使用 HTML/PDF，详细数据可另附 CSV；Markdown 保留为聊天呈现格式。

报告快照至少保存请求窗口、实际窗口、生成时间、数据来源摘要、结构化指标/事件和渲染版本。是否长期落库可按审计要求决定；如果第一阶段只做短期查看，可先使用有 TTL 的缓存，但不能让同一个报告编号指向不同数据。

### 6.5 阈值与“异常”必须克制

在没有设备额定值、工况、厂家限值或业务阈值时，只做描述性统计，不根据“最大值看起来高”判异常。后续如要增加越限判断，阈值必须来自设备型号/测点目录或经过审批的配置，输出中同时给出：实际值、阈值、持续时间、来源和适用工况。

这也意味着当前模拟器的随机转速、温度和负载只能用于展示查询/趋势，不能用于推断根因。建议模拟数据带 `SIMULATED` 来源标记和场景编号，验收数据使用固定种子或固定数据集以便复现。

## 7. 前端宽度与报告展示

### 7.1 已定位的直接原因

当前后端仓库不包含用户前端，无法核对部署中的定制代码。但对 2026-08-04 的上游 `ageerle/ruoyi-web` 提交 `b725d7e8d74c7f05aa0c076ff32c403907270533` 进行只读核查后发现：

- [`src/pages/chat/layouts/chatWithId/index.vue`](https://github.com/ageerle/ruoyi-web/blob/b725d7e8d74c7f05aa0c076ff32c403907270533/src/pages/chat/layouts/chatWithId/index.vue#L755-L762) 的 `.chat-with-id-container` 固定 `max-width: 800px`；
- [`src/pages/chat/layouts/chatDefaul/index.vue`](https://github.com/ageerle/ruoyi-web/blob/b725d7e8d74c7f05aa0c076ff32c403907270533/src/pages/chat/layouts/chatDefaul/index.vue#L39-L48) 同样固定 `max-width: 800px`；
- 外层 `.chat-container` 已经跟随主内容区变化，左侧栏折叠也已经通过 CSS 变量改变主区 `margin-left`。

因此截图中的窄内容区很可能来自 800px 上限，而不是侧栏状态没有传递。实施前应在实际前端分支复核同名样式。

### 7.2 推荐用 CSS 流式宽度，不增加 JS 宽度监听

主内容区本来会随侧栏展开/折叠改变，可让聊天容器使用父容器百分比并设置合理上限，例如设计目标：

```scss
.chat-with-id-container,
.chat-defaul-wrap {
  width: min(92%, 1200px);
  max-width: none;
}

@media (max-width: 900px) {
  .chat-with-id-container,
  .chat-defaul-wrap {
    width: 100%;
  }
}
```

这只是目标写法示意，实际要结合当前前端的 padding 和消息气泡样式验证。侧栏展开后父容器变窄，92% 随之变窄；侧栏折叠后自动变宽，最多 1200px，无需在折叠事件中手工计算像素。

宽屏不能简单让所有文本铺满：

- 报告卡片、表格、趋势图可以使用全部可用宽度；
- 普通说明段落限制在约 `70—80ch`，保证阅读行长；
- 用户气泡保持内容自适应并设置合理最大比例；
- 移动端表格横向滚动，指标卡改为单列；
- Markdown 的 H1/H2 应降低尺寸和间距，报告更适合紧凑的信息卡层级，而不是连续的大标题。

## 8. 建议的实施顺序

### 阶段 0：先确认数据契约（P0，实施前置）

1. 确认每个数值字段的工程单位、精度、空值/异常值含义；
2. 确认 `status`、`status_word` 与运行/停止等模式的映射；当前 Java 实体甚至没有读取 `status_word`，不能猜；
3. 确认真实数据采样周期、时间字段、入库延迟和允许的新鲜度阈值；
4. 为数据源配置 `SIMULATED / REAL`，当前所有聊天和报告显式展示“模拟数据”；
5. 明确首批开放指标，未确认的指标保持禁用并返回清楚原因。

### 阶段 1：补齐独立运行查询能力（P0）

1. 将请求能力调整为 `QUERY_TELEMETRY / LOOKUP_FAULT_CODE / DIAGNOSE_FAULT / GENERATE_OPERATION_REPORT`；
2. 引入小型 `MetricCatalog` 和结构化 `TelemetryQuerySpec`；
3. 提取共享的遥测窗口标准化逻辑，避免转速等字段在诊断摘要阶段丢失；
4. 实现 `LATEST / AVG_SAMPLES / MIN / MAX / TREND`；
5. 区分 `EXACT_WINDOW` 和 `LAST_KNOWN_ALLOWED`；
6. 增加运行快照渲染器，运行查询不得进入诊断回答骨架；
7. 保留现有固定 Mapper、资产白名单、时间上限和服务端计算。

完成本阶段后，第三个问题和“运行状态误归诊断”可以一起解决，而不是分别补路由。

### 阶段 2：运行报告 V2（P0/P1）

1. 报告改为以运行事实为主，诊断为可选章节；
2. 增加四维状态条、执行摘要、关键指标、统计表、事件生命周期、数据质量和模拟数据标签；
3. 聊天预览至少展示关键指标和主趋势，不再只给简短结论；
4. 前端消费结构化报告数据生成图表，LLM 不生成数值和图表数据；
5. 后续固化 `ReportSnapshot`，查看与下载使用同一报告编号和数据快照；
6. 需要正式流转时再增加 PDF/CSV，不在第一步同时建设复杂报表平台。

### 阶段 3：前端自适应与体验（可与阶段 2 并行）

1. 在实际用户前端分支复核 800px 限制；
2. 改为依赖主内容容器的流式宽度，设置约 1200px 上限和移动端断点；
3. 普通文本限制行长，图表/表格使用宽区；
4. 为报告提供“查看完整报告/下载同一报告”的真实按钮，而不是正文中的提示语；
5. 验证侧栏展开、折叠、浏览器缩放和常见分辨率。

### 阶段 4：真实数据接入后的增强（暂不实施）

真实数据、阈值和业务反馈稳定后，再评估：

- 时间加权平均；
- 额定值/工况相关阈值；
- 运行/停止时长与利用率；
- 多设备/班次报告；
- 趋势异常检测和根因模型。

这些都不应在当前模拟数据阶段提前建设。

## 9. 文件级改造范围建议

本轮不修改代码。后续实施时预计集中在以下范围：

| 范围 | 建议职责变化 |
| --- | --- |
| `FaultRequestPlanner` / `FaultRequestPlan` / `FaultTaskType` | 改为能力 + 参数规划，指标和操作来自服务端目录 |

## 10. 验收场景

### 10.1 运行查询

1. `查询 G120电机1 状态`：返回数据新鲜度、运行模式、关键运行值和事件状态；不出现“判断依据/根因建议”等诊断模板；
2. `G120电机1 此时转速是多少`：返回实际转速、单位、观测时间；数据过期时写“最后已知值”，不写“当前”；
3. `统计 G120电机1 过去一小时的转速平均值`：返回精确窗口内采样平均、单位、样本数、完整率；窗口无数据时不换窗；
4. `画出最近一小时设定转速和实际转速趋势`：返回同单位双曲线、时间范围、数据缺口；
5. 查询未开放指标：说明“不支持/单位未确认”，不得回退为故障诊断澄清语。

### 10.2 知识与诊断

6. `A07089 是什么意思`：只查询知识库，明确未读取设备遥测；
7. `诊断 G120电机1 最近半小时报警`：执行诊断，观测事实、知识解释和根因边界分开；
8. 运行查询中发现报警：只报告事件事实并提示“如需根因分析可继续诊断”，不能自动声称已诊断。

### 10.3 报告

9. `生成 G120电机1 最近一小时运行报告`：包含模拟数据标签、四维状态、关键指标、主趋势、事件、数据质量和限制；
10. 没有故障码但运行指标存在：报告仍然有完整运行内容，不能只剩“未发现故障”；
11. 指定窗口无数据：报告保持原请求窗口并说明无数据，不能回退为另一段历史报告；
12. 查看和下载相同 `reportCode`：数据窗口、摘要和来源摘要一致。

### 10.4 前端

13. 侧栏展开/折叠时内容区平滑变宽/变窄，不需要刷新；
14. 1440px 及以上屏幕报告图表/表格明显宽于当前 800px；普通正文行长仍可读；
15. 1024px、768px 和手机宽度下无正文截断，宽表可横向滚动。

## 11. 最终决策摘要

本次建议可归纳为五条：

1. **运行状态不是故障诊断**：分别输出数据状态、运行模式、事件状态和诊断结论；
2. **增加的是通用但受控的遥测查询能力，不是更多问句分类**：指标目录 + 标准聚合覆盖转速、温度、负载等问题；
3. **运行报告以运行事实、KPI、趋势和事件为主体**：诊断只是可选章节，报告内容由结构化数据决定；
4. **查询语义必须精确**：统计/报告不允许自动换窗，当前值必须带时间和新鲜度；
5. **前端使用父容器驱动的流式宽度**：侧栏折叠自然改变可用宽度，图表用宽区，正文保留合理行长。

这套调整复用现有确定性查询、权限、知识库和证据链，不引入通用多 Agent、自然语言 SQL 或复杂报表平台，能同时解决四个表面问题及其共同根因。
