# 故障诊断 Agent 可信度与可读性改进方案

> 状态：待实施  
> 制定日期：2026-08-03  
> 适用范围：设备遥测诊断、运行状态查询及诊断结果展示

## 1. 背景

当前故障诊断 Agent 已经形成基本闭环：

```text
用户意图
  → 设备与时间范围解析
  → 遥测查询
  → 故障码/报警码提取
  → 知识库检索
  → 确定性规则判断
  → 证据记录
  → 回答生成
```

目前能够完成：

- 故障码知识查询；
- 设备运行状态查询；
- 基于遥测中显式代码的故障诊断；
- 知识来源与内部证据链记录。

由于当前主要使用模拟数据，系统还没有条件通过转速、电流、温度和负载等运行信号独立识别异常。因此本轮不扩展异常检测能力，优先解决会直接影响用户理解和系统可信度的三个问题：

1. 报警和故障的语义混淆；
2. 历史数据被描述成当前状态；
3. 证据编号没有变成用户可读证据。

本轮的核心原则是：**先保证事实分类正确、时间表达准确、判断依据可读，再考虑增加更复杂的诊断能力。**

## 2. 当前问题与代码原因

### 2.1 报警和故障的语义混淆

底层规则引擎已经分别处理 `faultCodes` 和 `alarmCodes`：

- 有故障码时返回 `FAULT_DETECTED`；
- 只有报警码时返回 `WARNING_DETECTED`；
- 报警不会自动升级为故障。

但遥测分析层目前直接相信数据库字段：

```text
fault_code → faultCodes
alarm_code → alarmCodes
```

如果模拟数据把 `A07089` 写入 `fault_code`，它就会被当成故障。对于当前使用的 SINAMICS G120，`A` 类代码表示报警，`F` 类代码表示故障，因此仅依赖字段名不够可靠。

此外，现有编排器只对 `faultCodes` 查询知识库。即使将 `A07089` 正确归入 `alarmCodes`，后续也可能无法得到对应的报警说明和处理建议。

回答生成层还存在两个缺口：

- 确定性事实主要展示已观测故障码，没有同等展示报警码；
- 给大模型的可信摘要主要包含故障码，没有完整传入已观测报警码。

### 2.2 历史数据被描述成当前状态

模拟数据停留在固定历史时间。用户查询“现在状态”时，请求窗口没有数据，系统会回退到设备最近一次可用数据。

当前回退信息存在于 `TelemetryQueryResult.fallbackToLatestData`，但组装 `DiagnosisResult` 时只被转换成一条自然语言限制说明：

```text
请求时间范围内没有遥测数据，已回退至该设备最近可用数据……
```

最终回答层无法通过稳定的结构化字段判断“这是历史回退结果”，容易在后文继续使用“当前状态”“当前检测到故障”等措辞。

同时，结果中缺少最后一条有效遥测的实际观测时间。当前的分析窗口结束时间不一定等于最后观测时间，也不能完全代替数据更新时间。

### 2.3 证据编号不可读

当前 `EvidenceReference` 只有：

```text
evidenceId + evidenceCode
```

因此回答只能展示：

```text
EV-004、EV-003、EV-002、EV-001
```

用户无法知道每个编号分别代表遥测记录、知识手册还是规则结果。

证据编号在回答链路中还被转换为普通 `Set`，展示顺序不应被依赖，可能出现与诊断执行顺序不同的排列。

另外，证据链中的“规则执行”和“结果组装”更接近内部审计步骤，不一定都需要在普通用户回答中展开。用户真正关心的是：系统看到了什么数据、依据什么资料、为什么得出这个结论。

## 3. 本轮目标

本轮完成后应满足：

1. `A` 类报警不会被描述成 `F` 类故障；
2. 故障和报警可以同时存在，并在回答中分别展示；
3. 使用历史回退数据时，第一句话明确说明当前状态无法确认；
4. 所有状态结论带有明确时间锚点；
5. 用户看到的是“遥测记录（EV-001）：……”而不是孤立的 EV 编号；
6. 结论、时间边界和证据摘要由服务端确定性生成；
7. 大模型仅负责整理知识说明和处置建议，不修改确定性事实。

## 4. 暂不处理的内容

为避免过度设计，本轮不做：

- 不引入通用多 Agent 或新的工作流框架；
- 不建立完整的多厂商故障码分类体系；
- 不设计 `FRESH/DELAYED/STALE/OFFLINE` 等多级新鲜度状态机；
- 不根据温度、电流、转速等指标自动推断故障；
- 不建设复杂的报警事件聚合和生命周期模型；
- 不重构现有证据哈希链和持久化机制；
- 不增加自动修改参数、复位设备或下发控制指令的能力；
- 不一次性设计四套大型回答模板。

## 5. 改进方案

### 5.1 P0：在遥测入口统一故障和报警语义

#### 5.1.1 修正模拟数据

首先修正模拟数据的数据契约：

- `A07089` 应写入 `alarm_code`；
- `F30899`、`F07016` 等故障码应写入 `fault_code`；
- `0` 和空值表示没有对应代码。

后端归一化是防御措施，不能替代数据源修正。

#### 5.1.2 增加 G120 代码类型归一化

在遥测分析边界增加简单的确定性分类：

| 代码格式 | 归类 | 用户表述 |
| --- | --- | --- |
| `F` + 数字 | 故障 | 检测到故障码 |
| `A` + 数字 | 报警 | 检测到报警码 |
| `0` 或空值 | 无代码 | 不展示 |
| 其他格式 | 未知 | 检测到未识别代码，不升级为故障 |

当字段与代码类型冲突时，例如 `fault_code=A07089`：

1. 当前 G120 场景下按代码前缀归类为报警；
2. 记录“字段与代码类型不一致”的数据质量问题；
3. 不返回 `FAULT_DETECTED`；
4. 不让未知格式默认进入故障列表。

当前只支持 G120，不需要立即抽象多厂商规则。以后接入其他厂商时，再按设备类型选择对应分类器。

#### 5.1.3 报警也进入知识查询

知识查询输入应覆盖本次观测到的故障码和报警码，同时保留类型：

```text
F30899 → FAULT
A07089 → ALARM
```

知识查询命中后，回答使用对应术语：

- “F30899 故障的资料说明……”；
- “A07089 报警的资料说明……”。

知识库只能解释代码的通用含义和处置方向，不能直接把资料原因写成本设备已经确认的根因。

#### 5.1.4 故障与报警分别输出

不需要增加大量诊断状态枚举。保留现有状态优先级，同时在回答中根据两个代码列表分别展示：

```text
故障：F30899
报警：A07089
```

如果两者同时存在，结论应写为：

> 检测到 F30899 故障，同时存在 A07089 报警。

不能因为故障优先级更高，就隐藏报警信息。

### 5.2 P0：结构化保存数据时间边界

#### 5.2.1 保留必要的时间字段

至少将以下信息传递到最终诊断结果和回答生成层：

- 请求时间范围；
- 实际分析时间范围；
- `fallbackToLatestData`；
- `latestObservedAt`，即最后一条有效遥测的业务时间。

回答层必须根据结构化字段决定时态，不能从 `limitations` 中文本中推断。

#### 5.2.2 第一阶段采用简单时间规则

当前阶段不增加复杂新鲜度状态机，先执行以下规则：

1. `fallbackToLatestData=true`：当前状态无法确认，只能描述最近一次数据；
2. 未使用回退：状态描述仍使用“截至具体时间”，避免无时间锚点的“当前正常”；
3. 用户明确查询历史时段：使用“在该时间范围内”；
4. 没有有效数据：返回数据不足，不推断设备正常或故障。

推荐表达：

```text
当前状态无法确认。
设备最新数据时间为 2026-07-19 15:04:11。
最近一次可用数据中出现过 A07089 报警，未发现 F 类故障码。
```

不推荐表达：

```text
G120电机1当前状态为检测到故障。
```

真实数据接入并明确采样周期、传输延迟后，再单独增加可配置的新鲜度阈值。

### 5.3 P1：将证据编号转换为可读依据

#### 5.3.1 保留 EV 编号

`EV-001` 等编号继续用于数据库证据链、哈希校验和审计，不需要改成另一套编号体系。

需要增加的是用户展示信息，例如：

```text
证据编号
证据类型
证据标题
一句话摘要
观测时间或来源文档
```

#### 5.3.2 服务端确定性生成证据摘要

示例：

```text
遥测记录（EV-001）：
G120电机1，2026-07-19 14:50:01—15:04:11，
共245条有效记录，出现 A07089。

手册资料（EV-002）：
《G120故障手册》A07089 条目，代码类型为报警。

判断规则（EV-003）：
A类代码归入报警；历史回退数据不能表示当前状态。
```

证据摘要必须由服务端根据实际证据记录生成。大模型只能引用已生成的摘要，不能根据编号猜测证据内容。

#### 5.3.3 区分用户依据和内部审计

普通回答默认展示：

- 遥测观测证据；
- 知识手册来源；
- 必要的判断规则说明。

以下信息保留在内部证据详情或后台审计中：

- 规则步骤开始/结束记录；
- 结果组装步骤；
- 请求哈希、结果哈希和证据链哈希；
- 内部数据库 ID。

#### 5.3.4 保证展示顺序稳定

用户证据使用有序列表，按照结论形成顺序输出：

1. 遥测数据；
2. 知识资料；
3. 判断规则；
4. 结果记录。

不要依赖普通 `Set` 的迭代顺序。

### 5.4 P1：固定回答骨架，提高可读性

设备诊断先使用一套统一模板，空内容按需隐藏：

```text
结论
  → 最近一次观测
  → 代码说明
  → 建议
  → 判断依据
  → 结论边界
```

其中：

- 结论、时间、故障列表、报警列表、证据摘要由服务端渲染；
- 大模型只生成知识说明和处置建议；
- 数据质量详情放在回答底部或折叠区域；
- 不向普通用户展示 `FAULT_DETECTED`、`partial`、`requestId` 等内部字段；
- 回答第一句话直接给出“有故障、存在报警、未发现显式故障，或当前无法确认”。

## 6. 推荐回答示例

用户提问：

> G120电机1现在有没有故障？怎么处理？

推荐回答：

```text
## 结论

当前状态无法确认。
设备最新数据时间为 2026-07-19 15:04:11，属于历史数据。

## 最近一次观测

- 故障：未发现 F 类故障码
- 报警：A07089
- 数据范围：2026-07-19 14:50:01—15:04:11

## 报警说明

A07089 是报警，不是 F 类故障。资料显示，该报警通常与单位切换后
激活功能模块受阻有关，但尚未确认本设备的实际参数配置。

## 建议

1. 核对 p0100、p0505 当前值。
2. 确认近期是否执行过单位切换或功能模块激活。
3. 修改参数前先备份，并在修改后重新采集最新数据进行验证。

## 判断依据

- 遥测记录（EV-001）：245条有效记录中出现 A07089。
- 手册资料（EV-002）：A07089 条目，类型为报警。

## 结论边界

当前只能确认历史数据中出现过该报警，不能确认设备现在仍存在报警，
也不能仅凭代码确认本设备的实际根因。
```

## 7. 建议修改范围

预计主要涉及：

- `TelemetryDataAnalyzer`：归一化 F/A 代码类型并计算最后观测时间；
- `TelemetryQueryResult`：携带最后观测时间和回退标记；
- `FaultDiagnosisOrchestrator`：让报警码也进入知识查询；
- `DiagnosisResult` / `DiagnosisResultAssembler`：保留结构化时间边界；
- `FaultExecutionResult`：分别提供已观测故障码和报警码，保留证据顺序；
- `FaultDiagnosisChatService`：按固定骨架渲染结论、时间和可读证据；
- `FaultAnswerGenerator`：只整理知识解释和建议，并接收完整报警事实；
- `FaultAnswerSafetyValidator`：同时校验 F 类故障码和 A 类报警码；
- 对应的遥测分析、规则引擎、回答生成和安全校验测试。

本轮不要求修改现有证据链表结构。如果展示信息能够在诊断过程中确定性组装，可以先通过结果 DTO 提供；是否持久化更多展示字段可在后续根据审计需求决定。

## 8. 实施顺序

### 第一阶段：P0 语义和时间修正

1. 修正模拟数据中的 `fault_code` / `alarm_code`；
2. 在遥测入口增加 G120 的 F/A 类型归一化；
3. 报警码进入知识查询、回答摘要和安全校验；
4. 将回退标记和最后观测时间传递到最终结果；
5. 历史回退回答强制使用“当前状态无法确认”。

### 第二阶段：P1 可读证据和回答模板

1. 为 EV 编号生成证据类型、标题和一句话摘要；
2. 用户证据改为有序列表；
3. 将内部规则步骤和结果组装移出回答主体；
4. 使用统一的简洁回答骨架；
5. 原始记录数、重复数、缺口数等降级为数据质量详情。

### 第三阶段：验证与观察

1. 补齐自动化验收用例；
2. 使用三台模拟设备执行端到端验证；
3. 检查回答中是否仍出现错误时态和错误代码类型；
4. 观察真实使用反馈后，再决定是否增加数据新鲜度分级和运行指标展示。

## 9. 验收标准

以下条件全部满足后视为本轮完成：

1. `A07089` 即使误写入 `fault_code`，回答也只能称为报警，不能出现“显式故障”；
2. `F30899`、`F07016` 等 F 类代码仍正确归为故障；
3. 同时存在 F 类故障码和 A 类报警码时，两者分别展示；
4. 未知格式代码不会被默认升级为故障；
5. 报警码可以查询知识说明，并使用“报警”措辞；
6. 查询“现在状态”但回退到历史数据时，第一句话为“当前状态无法确认”或同义明确表达；
7. 所有状态结论包含最新数据时间或明确历史时间范围；
8. 回答不能只展示孤立的 `EV-xxx` 编号，每个用户可见编号都有可读摘要；
9. 用户证据按诊断执行顺序展示，不倒序、不随机；
10. 知识库原因必须标记为资料解释或可能原因，不能描述成本设备根因已经确认；
11. 没有持久化证据时不得生成虚假 EV 编号；
12. 回答主体不展示 `partial`、`requestId` 和内部英文状态；
13. 相关自动化测试通过，并完成一次真实 SSE 端到端验证。

## 10. 后续可选项

本轮稳定后，可根据真实遥测数据逐步评估：

- 按实际采样周期增加数据新鲜度阈值；
- 展示最新转速、电流、温度、负载和短期趋势；
- 将连续重复代码聚合成报警/故障事件；
- 增加报警是否恢复、持续时长和最后活动时间；
- 按设备型号和固件版本筛选知识资料；
- 增加操作步骤的预期结果、风险等级和升级条件。

这些能力不应阻塞本轮三个核心问题的修复。
